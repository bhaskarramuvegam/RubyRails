= Tracker Fields Configuration

Lets administrators "promote" selected custom fields so they render inside
the standard fields area of the issue form (next to Priority, Assigned To,
Category, etc.) instead of down in the separate "Custom fields" box.

Configuration is per *project* and per *tracker*, and is done entirely from
<b>Administration > Plugins > Tracker Fields Configuration</b>. The settings
page always reads the live list of projects, trackers and custom fields from
this Redmine instance - nothing is hard-coded, so newly added projects,
trackers or custom fields show up automatically.

== How it works

For each project you configure, and each tracker within that project, you
pick:

1. Which custom fields should be promoted.
2. Which standard field each promoted custom field should appear directly
   after (e.g. "insert Root Cause after Priority").

On the issue form, the plugin moves the promoted custom field's existing
row (label + input) to sit right after the chosen standard field. It does
not duplicate, re-render or copy the field - it is the exact same input
element, just relocated - so validation, required-field checks, and any
other plugin's interaction with that field keep working unchanged. If every
custom field configured for a tracker is promoted, the (now empty) "Custom
fields" box is hidden.

The move re-applies correctly when the tracker or project dropdown is
changed on the new-issue form: the plugin embeds rules for every tracker in
the issue's project up front and watches the attributes box for the Ajax
swap Redmine performs on tracker/project change, reapplying automatically.
This works the same way on both new-issue and edit-issue forms.

The promotion also applies to the read-only issue *show* page, which uses
completely different markup than the form (div-based rows instead of
labeled inputs). There, the promoted custom field's row is matched by its
+cf_<id>+ CSS class and the target standard field's row is found by
matching its label text (e.g. "Priority:") against the field's translated
name, rather than assuming a class name - so it degrades gracefully if a
theme changes markup, instead of silently misplacing a field.

== Hide / unhide fields (separate feature)

Independent of field promotion above: for each project + tracker, you can
also completely hide any standard field (Priority, Assigned To, Due Date,
etc.) or custom field, from both the issue form and the show page. This is
configured in its own "Hide / Unhide Fields" section on the same settings
page, with its own project picker.

This feature is implemented in its own files (+HiddenFieldsHooks+, its own
controller action/route/partial, its own settings key
+project_tracker_hidden_fields+, its own JS namespace) so it cannot
interfere with field promotion - each one only reads/writes its own
settings key and has no code path that touches the other's.

Hiding a *required* field can prevent saving an issue unless that field
already has a usable default value, since the hidden input is still part
of the form (just visually hidden) and Redmine still validates it - give
it a sensible default before hiding it if it's required.

=== Hiding fields from other plugins (e.g. Redmine Agile's "Sprint")

Fields injected by other plugins (not a Redmine CustomField) can't be
auto-discovered, so they aren't listed automatically. Instead, in the
"Other fields" area at the bottom of each tracker's hide/unhide list, you
register one manually:

1. Right-click the field on the issue form and choose Inspect.
2. Find its HTML +id+ attribute, e.g. <tt>id="issue_agile_data_attributes_agile_sprint_id"</tt>.
3. Enter everything after +issue_+ as the id, and a label matching the
   field's on-screen name exactly (this is used to find it on the show
   page, where fields aren't identified by id).
4. Click *+ Add* - it now appears with its own checkbox, same as any
   standard or custom field.

The Hide/Unhide Fields box always shows a "Registered 'Other Fields'
(all projects)" summary - independent of which projects happen to be
checked in the bulk tree, since that resets to unchecked on every page
load. Without this, a field registered via bulk mode looks like it
"disappeared" after a reload, when it's actually just that its tracker's
panel isn't shown again until the same projects are re-checked.

It's grouped into a collapsed-by-default accordion per project (click to
expand). Each field's "Hidden" checkbox and Remove button work directly
from this summary and take effect on the page's normal Save - no need to
open the single-project or bulk panel just to toggle or remove one you
already know about.

The summary always shows one row per unique (project, tracker, field) -
if a field was registered more than once for the same tracker (the bulk
"+ Add" flow used to allow this if you clicked it again in a later
session without noticing the field was already listed), saving from this
table collapses those duplicates back down to one automatically.

The summary is the *only* place that can toggle or remove an
already-registered field. Earlier, the bulk panel's "already registered"
list also had its own checkbox for this, but that meant two independent
parts of the same page could submit different values for the same field
in one save - specifically, the single-project panel's and bulk mode's
"preserve everything you're not actively editing" safeguards always
carried forward whatever the field's *previous* state was, so removing or
unhiding it via the summary got silently undone by that stale copy on the
very next save. Both of those safeguards now explicitly skip
project_tracker_extra_fields/_labels and any ext_-prefixed hidden-field
entry, since the summary already covers that data unconditionally for
every project; the bulk panel's "already registered" list is read-only
now, purely for awareness while picking projects.

== Configuring multiple projects at once

Both the field-promotion section and the hide/unhide section have a mode
toggle at the top: *Configure one project* (the original flow, unchanged)
or *Configure multiple projects*. The bulk mode's project tree is
collapsed behind a "Show project list" toggle by default (with a live
count of how many projects are currently checked next to it); each parent
project with sub-projects gets its own +/- button to expand just that
branch. Checking a parent project automatically checks (and visually
cascades to) all of its sub-projects, matching how Windows' "Turn Windows
features on or off" dialog behaves - collapsing a branch doesn't affect
which boxes are checked, it's purely a display choice. The tracker/field
panel below the tree shows the *union* of trackers enabled on any checked
project, and pre-fills from current state whenever every checked project
that has that field agrees (leaving it blank with a "mixed" badge when
they don't), so opening bulk mode and saving without changing anything
doesn't silently clear existing configuration.

<b>Saving in bulk mode overwrites</b> the checked projects' configuration
for every tracker shown in the panel - it isn't a merge. Leaving a
tracker's fields unchecked and saving clears that tracker's configuration
for every checked project that has it. This is intentional (it's what
"configure once, apply to many" means), but it means you should treat the
bulk panel as "this is what I want these trackers to look like now" rather
than as an editor of any one project's current settings. Projects you
don't check are left completely untouched.

The hide/unhide bulk panel also handles "Other fields" (non-CustomField
plugin fields like Agile's Sprint):

* Already-registered fields show up unioned across the checked projects,
  each as its own toggle scoped to just the projects that actually have
  it registered - checking/unchecking one follows the same overwrite
  rules as standard/custom fields.
* A "+ Add to all checked projects" form registers a brand new field
  (label + id, same as the single-project panel) across every checked
  project that has that tracker, and hides it by default - this part
  does *not* follow the overwrite rule; it only adds, and any project's
  existing extra-field registrations are always carried forward
  untouched by a bulk save.
* Add fields before changing which projects are checked - further tree
  changes reload the panel and the newly-added row's visual confirmation
  goes with it, though the registration itself is still saved.

== Installation

No database migration is required. This plugin only uses Redmine's built-in
plugin settings storage (Setting.plugin_tracker_fields_configuration).

The settings page loads the project list up front (id/name only) and fetches
one project's tracker/custom-field table at a time via a small admin-only
AJAX endpoint (+TrackerFieldsConfigurationController#project_fields+) when
you pick it from the dropdown, caching it in the page so switching back
doesn't re-fetch or lose your edits. This keeps the page fast even on
instances with many projects and/or many custom fields per tracker.

1. Copy/unzip this plugin into your Redmine +plugins+ directory as
   +tracker_fields_configuration+.
2. Restart Redmine.
3. Go to Administration > Plugins > Tracker Fields Configuration > Configure,
   pick a project, expand a tracker, and choose the fields to promote.

== Notes

* If a custom field is checked but no "insert after" standard field is
  chosen for it, it is left in its normal position (nothing happens for it).
* The "insert after" choices offered for a tracker are limited to the
  standard fields actually enabled for that tracker (via +Tracker#core_fields+),
  plus Status and Priority which are always present.
* Disabling the plugin (General > Enable Plugin) restores every field to its
  normal position without needing to clear individual project/tracker
  selections.
